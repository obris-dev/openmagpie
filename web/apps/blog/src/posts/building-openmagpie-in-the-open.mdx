Social listening has always come with the same three strings attached: a per-seat license, a black-box relevance model you can't inspect, and your data sitting on a vendor's server. You pay to find out what people are saying about the things you care about, and in exchange you hand over the record of everything you searched for.

We think that trade is backwards. So we're building OpenMagpie the other way around, and building it in the open.

## Describe what you care about, in a sentence

Most tools make you think in boolean keyword soup: `("our product" OR "ourproduct") AND (bug OR broken OR "not working") -sale`. You spend more time tuning the query than reading the results, and you still miss the post that phrased it differently than you guessed.

OpenMagpie starts from a sentence instead. You describe what you're listening for the way you'd describe it to a coworker, and a relevance judge decides whether each incoming item is worth your attention. A watch is just that description plus the feeds it reads:

```bash
magpie feed create --name "r/selfhosted" --kind reddit
magpie watch create --name "deployment pain" \
  --feed r-selfhosted \
  --filter "someone struggling to self-host an app and asking for help"
```

No keyword lists to maintain. When the way people talk about a problem shifts, the description still holds.

## Open source, and yours to run

Every part of OpenMagpie is open source and self-hostable. You can read exactly how relevance is judged, point it at any OpenAI-compatible model (including one running on your own hardware), and keep the whole pipeline (the feeds you poll, the threads you surface, the runs you export) on infrastructure you control. Nothing leaves your box unless you decide it should.

That's not a compliance checkbox. It's the difference between a tool you rent and a tool you own. When the relevance judge gets something wrong, you can see why. When you want to add a source we don't ship, the connector interface is right there.

## Why a blog

This is the first post because we'd rather show the work than announce it. We'll write here about the parts we think are interesting: how the relevance judge is prompted and where it falls down, how we keep a shared type contract honest across a Python server, a CLI, and a web app, and what we learn running OpenMagpie on our own conversations.

If any of that sounds useful, the code is on [GitHub](https://github.com/obris-dev/openmagpie), and you can start [here](https://openmagpie.ai). I'd love to hear what you're trying to listen for.
